# Repository Review — what to implement, what is missing

**Reviewed:** 2026-08-14 · commit as cloned from `main`
**Method:** every claim below was verified by running the code or querying the committed data on this machine. Nothing is taken from the existing audit documents on trust — several of them are now wrong, which is itself finding #1.

## 0. The headline: the repo has moved, the documentation has not, and the dashboard is serving pre-fix numbers

The single most important fact about this repository today is one that none of its four audit documents record:

**The corrected Earth Engine export has already landed.** `Remote Sensing & Data Engineering/Dataset/dataset.csv` now contains:

| Column | Status | Evidence |
|---|---|---|
| `NDVI` | **corrected** — range −0.416 to **0.781** | the pre-fix export capped at 0.386 |
| `LandCover` | **present** — ESA WorldCover codes | 3,752 tree · 3,523 built-up · 573 crop · 149 water · 79 grass · 44 wetland · 24 bare |
| `NDBI` | **present** | correlates with LST at **+0.609** |
| `Vegetation` | **present** — continuous 0–1 fraction | mean 0.556, 4,159 distinct values |
| `Latitude` / `Longitude` | **present** as real columns | no longer need deriving from `.geo` |

`IMPROVEMENTS.md` P0 items 1–2, `INTEGRATION_AUDIT.md` Finding 6, and `docs/08-limitations.md` all describe this work as outstanding. It is done. Those documents are now actively misleading — they will make a reader distrust numbers that are fine and trust numbers that are not.

**And the downstream modules never caught up.** Three states coexist in one repository:

```
dataset.csv ................ CORRECTED  (NDVI max 0.781, has LandCover)
  ├─ Decision-Support/*.csv  FRESH      (has land_cover column, 4,157 rows)
  │    └─ but its script CANNOT RUN (see A1)
  └─ ML/Results/*.csv ........ STALE     (NDVI max 0.386 — the pre-fix data)
       └─ frontend/data/grid.geojson  ← THE LIVE DASHBOARD SERVES THIS
```

Verified: `Machine Learning & Prediction/Results/preprocessed.csv` has NDVI max **0.386**. `frontend/data/grid.geojson` is byte-identical (md5 `0c66e0e2…`) to `Machine Learning & Prediction/Results/grid.geojson`, which was built from that stale file.

Re-running the ML pipeline against the corrected dataset (I did this in a scratch copy — it works, no code changes beyond the path fix in A1) changes **970 of 8,144 cells' recommended action**, or 11.9% of the map, and shifts the programme cost from ₹1,604,626,620 to ₹1,589,157,842.

**Neither Python module is currently reproducible end-to-end.** Decision-Support has fresh outputs but a script that crashes; ML has a script that runs but stale outputs. Both defects trace to the same one-line cause.

## A. Blockers — nothing else can be re-run until these are fixed

### A1. Both Python pipelines crash on a clean clone: the dataset was renamed, the readers were not

`Dataset/Guwahati_Urban_Heat_Dataset.csv` was renamed to `Dataset/dataset.csv` (the Remote Sensing `SPEC_AUDIT.md` item 13 records the rename as "✅ Done"). Neither consumer was updated.

Reproduced on a clean clone:

```
FileNotFoundError: [Errno 2] No such file or directory:
'.../Decision-Support/../Remote Sensing & Data Engineering/Dataset/Guwahati_Urban_Heat_Dataset.csv'
```

**This gates every other item in this document.** Two-line fix:

| File | Line | Change |
|---|---|---|
| `Machine Learning & Prediction/scripts/preprocess.py` | 33 | `/ "Guwahati_Urban_Heat_Dataset.csv"` → `/ "dataset.csv"` |
| `Decision-Support/member3_decision_support.py` | 59 | `"Guwahati_Urban_Heat_Dataset.csv"` → `"dataset.csv"` |

Also update the docstrings that name the old file (`preprocess.py:9`, `member3_decision_support.py:22`) and `docs/02-setup-and-build.md:107`.

The deeper fix: **no module should hardcode the filename twice.** Put the path in one place both modules import, or have `preprocess.py` glob `Dataset/*.csv` and assert exactly one match. A rename should not be able to silently break two modules again.

### A2. The live dashboard recommends planting trees in the Brahmaputra

This is the most serious defect in the repository, and it is publicly visible on the deployed site.

`Machine Learning & Prediction/scripts/preprocess.py:150-152` selects exactly seven columns forward:

```python
out = out[["grid_id", "LST", "NDVI", "Heat_Risk", "Latitude", "Longitude", "geo_json"]]
```

`LandCover`, `NDBI`, and `Vegetation` — the three columns the corrected export added — are **discarded before any downstream step sees them**. `ACTION_TABLE` (`tier_and_recommend.py:66-73`) is therefore keyed on `(priority, vegetation_class)` alone, with no land-cover input, and assigns a physical intervention to any cell that is merely hot.

Joining the **committed, live** `frontend/data/grid.geojson` against `dataset.csv`'s `LandCover` on `grid_id` (all 8,144 rows matched):

| Land cover | Cool roof | Green park | None | Tree cover |
|---|---|---|---|---|
| built_up | 22 | **1,643** | 68 | **1,790** |
| water | 0 | **96** | 45 | **8** |
| wetland | 0 | **39** | 0 | **5** |
| tree | 21 | **1,739** | 1,911 | 81 |
| crop | 36 | 490 | 8 | 39 |
| grass | 2 | 55 | 4 | 18 |
| bare | 0 | 10 | 0 | 14 |

- **148 water and wetland cells** are assigned tree planting or a park.
- **3,433 built-up cells** are assigned a ground-level intervention — parks and tree cover on rooftops and roads.
- **1,739 cells that ESA WorldCover already classifies as tree cover** are assigned "build a park here."

The costed programme therefore includes hundreds of millions of rupees of interventions that are physically impossible. Any domain reviewer will find this in the first minute.

**The fix already exists in this repository and is not being used.** `Decision-Support/member3_decision_support.py:107-152` implements exactly the right suitability filter — `NEVER_TOUCH = ["water", "wetland"]`, `ROOF_ELIGIBLE = ["built_up"]` (roof interventions only), `GROUND_ELIGIBLE = ["bare_sparse", "grassland", "cropland"]` (ground interventions only), and an `ALREADY_GREEN` short-circuit for existing tree cover. That module's committed output has no water/wetland interventions at all.

**Implement:** carry `LandCover` (and `NDBI`, `Vegetation`) through `preprocess.py`, and port Decision-Support's suitability gate into `tier_and_recommend.py` **before** `ACTION_TABLE` is consulted. This is the concrete form of what `INTEGRATION_AUDIT.md` vaguely called "pick one recommendation engine": don't pick — the ML module owns the frontend contract and the geometry, Decision-Support owns the suitability logic. Move the logic, keep the contract.

### A3. Re-run the ML pipeline and re-export; add the missing copy step

Once A1 and A2 land, `preprocess.py → tier_and_recommend.py → export_grid_geojson.py` must actually be run and the outputs committed. Verified working on corrected data in a scratch copy.

There is also an **undocumented manual step**: `export_grid_geojson.py` writes to `Machine Learning & Prediction/Results/grid.geojson`, but the dashboard reads `frontend/data/grid.geojson`. Somebody copies that file by hand. Nothing in the repo records this, and nothing detects drift if it is forgotten. Either have the export script write both paths, or add a build script. Right now the two are identical only by luck.

## B. Correctness defects

### B1. Every script prints a warning that is now false

`preprocess.py:117-125`, `tier_and_recommend.py:171-174`, `train_regression.py:161-164`, and `export_grid_geojson.py:102-104` all emit variations of:

> `WARNING: NDVI is passed through UNCORRECTED (raw-DN artifact, SPEC_AUDIT #3)`

Against the current dataset this prints alongside `NDVI observed range: -0.416 to 0.781` — the message contradicts the number on the next line. The saved model pickle also records `"ndvi_corrected": False` (`train_regression.py:246`) and `metrics.json` carries the same false flag.

**Implement:** rather than deleting the warnings, make them *derived* — check `df["NDVI"].max() > 0.5` and warn only if the data actually looks uncorrected. A hardcoded caveat about data is a caveat that will be wrong the moment the data changes, which is exactly what happened.

### B2. The vegetation split should now use real data, not a workaround quantile

`tier_and_recommend.py:58` sets `VEGETATION_SPLIT_QUANTILE = 0.50`, with a comment explaining it is a deliberate workaround because uncorrected NDVI had a p95 of only ~0.295 so the literature threshold of 0.3 would have collapsed the table. That reasoning no longer applies — NDVI now reaches 0.781 and the median is **0.452**.

Using the median now mislabels every cell in the 0.30–0.45 band as `sparse` when it is genuinely vegetated.

`IMPROVEMENTS.md` item 2 says to switch to an absolute NDVI of 0.3. **Better option, now available:** the dataset carries a `Vegetation` column — a continuous 0–1 vegetation fraction from WorldCover, correlating 0.776 with NDVI and −0.455 with LST. A direct fraction beats a threshold on an index. Split on `Vegetation` (e.g. ≥ 0.5) instead of on NDVI at all.

### B3. The regression drops the strongest available predictor

`train_regression.py:53` — `BASE_FEATURES = ["NDVI", "Latitude", "Longitude"]`.

Measured on the current dataset:

| Feature | Correlation with LST | In the model? |
|---|---|---|
| `NDBI` | **+0.609** | ✗ dropped by `preprocess.py` |
| `Vegetation` | −0.455 | ✗ dropped by `preprocess.py` |
| `NDVI` | −0.398 | ✓ |

The built-up index is the single strongest linear predictor of surface temperature in the data and the model never sees it. The module README explains the weak NDVI signal as an artifact of the uncorrected export; that explanation has expired, and the real gap is a missing feature. Adding `NDBI` and `Vegetation` is a few lines once A2 carries them through.

Keep quoting the **spatial-block** R², not the random-split 0.938 — that guidance in `IMPROVEMENTS.md` item 6 is still correct and still important.

### B4. Decision-Support writes its outputs to the current working directory

`member3_decision_support.py:201, 205, 209` call `to_csv("recommendation.csv")` with a bare relative name. Run the script from anywhere but its own directory and three CSVs are scattered wherever you happened to be standing. Fix to `os.path.join(SCRIPT_DIR, ...)` — the file already computes `SCRIPT_DIR` on line 56 for its input.

### B5. Decision-Support has no `main()` and no function boundaries

The entire module is top-level statements executing on import (lines 85–214). It cannot be imported, cannot be unit-tested, cannot be called with different parameters, and writes files as a side effect of `import`. Wrap in functions with an `if __name__ == "__main__":` guard, matching the convention the ML module already follows.

### B6. Two divergent copies of the Earth Engine script

`GEE/urban_heat_analysis.js` (438 lines) and `Remote Sensing & Data Engineering/GEE/urban_heat_analysis.js` (605 lines) are different files (differing md5). Both contain a `0.0000275` rescale and both add WorldCover, but they are not the same program.

**Which one produced the committed `dataset.csv` cannot be determined from what is in the repository.** That is the finding — not that one is wrong. The upstream stage of this project has ambiguous provenance. Delete one, or make the root copy a pointer to the canonical one, and record which produced the committed export.

### B7. The QGIS project still has three unresolvable layers

`IMPROVEMENTS.md` item 5 — still open, still accurate. `Remote Sensing & Data Engineering/QGIS/guwahati_heat_project.qgz` references `./guwahati_boundary.geojson` (wrong directory — the file is in `Boundary/`), a `.shp` that exists nowhere in the repo, and an absolute path into a `Downloads/` folder on the original author's machine.

## C. What is missing entirely

### C1. No tests. None, anywhere.

No `test_*.py`, no `conftest.py`, no test directory. The only validation in the project is `export_grid_geojson.py`'s `validate()`, which is genuinely good but checks schema, not logic.

Every defect in section A would have been caught by a test that took under ten lines:

```python
def test_no_intervention_on_water():
    df = load_recommendations()
    water = df[df.land_cover.isin(["water", "wetland"])]
    assert (water.recommended_action == "None").all()

def test_source_dataset_exists():
    assert SOURCE_CSV.exists()

def test_committed_outputs_match_committed_inputs():
    # regenerate into a temp dir, compare to what is committed
```

**Implement a `pytest` suite covering:** the source path resolves; the action table's suitability rules (no ground work on water/built-up); cost and cooling lookups raise on unknown actions rather than returning NaN; and a staleness check that regenerating from `dataset.csv` reproduces the committed CSVs. That last one is the test that would have caught this entire review.

### C2. No CI

No `.github/` directory. Add a workflow that installs `requirements.txt`, runs the full pipeline from `dataset.csv`, and fails if the committed outputs differ from the regenerated ones. That single check makes the stale-data class of bug impossible to merge.

### C5. Ecology, cost, and cooling numbers are still unvalidated placeholders

Still true, still worth stating in any presentation: `COOLING_C` (`tier_and_recommend.py:126-131`) is a flat 0.8 / 1.0 / 2.0 °C per action type, borrowed from Decision-Support, which itself labels them "placeholder engineering estimates for a hackathon demo." Nothing is fitted to Guwahati.

Also note the two modules use **different unit rates** for the same intervention — ML uses ₹150/m² for trees at 25% coverage (`COST_HEURISTICS`), Decision-Support uses ₹37.5/m² at full cell area (`RATE_TREE_COVER`). Both arrive at a similar per-cell figure by different routes, which is worse than disagreeing openly: it looks like agreement. Pick one rate table and have both modules import it.

**Implement:** a single `constants.py` (or JSON) at repo root holding unit rates, cooling assumptions, and land-cover mappings, imported by both modules. One number, one place.

## D. Engineering and delivery

### D1. Repository carries duplicate multi-megabyte data

| File | Size | Note |
|---|---|---|
| `frontend/data/grid.geojson` | 3.7 MB | identical to the ML output |
| `Machine Learning & Prediction/Results/grid.geojson` | 3.7 MB | identical to the above |
| `Remote Sensing & Data Engineering/Results/grid.geojson` | 4.4 MB | different schema — raw columns |
| `frontend/mock_data/grid.geojson` | 320 KB | superseded; still the fallback in `main.js:3` |
| `Dataset/dataset.csv` + two derived CSVs | ~9 MB | `preprocessed.csv` and `tiered.csv` are fully regenerable |

Roughly 12 MB of the repository is regenerable or duplicated. Consider committing only `dataset.csv` (the one artifact that genuinely cannot be regenerated without Earth Engine access) and generating the rest in CI.

### D2. The dashboard downloads 3.7 MB of GeoJSON before it renders anything

Every visitor fetches all 8,144 polygons up front. The `HeatField` renderer only ever uses each cell's centroid and bounds — the full polygon rings are downloaded and then averaged down to a point (`dataLoader.js:normalize`). Shipping centroids plus a bounding box instead of full rings would cut the payload several-fold with no visual change. Longer term: vector tiles, or a quantized binary format.

`vercel.json` sets a good cache header on `/frontend/data/*`, so repeat visits are fine. It is the first paint that suffers.

### D3. One unpinned CDN dependency

`frontend/index.html` loads `https://unpkg.com/leaflet-control-geocoder/dist/Control.Geocoder.js` with **no version pin**, while Leaflet (`@1.9.4`) and Chart.js (`@4.4.1`) are correctly pinned. An upstream major release breaks the deployed site with no commit. Pin it, and add SRI hashes to all three.

### D4. No dependency manifest for the frontend, no linting anywhere

No `package.json`, no ESLint, no formatter config, no `ruff`/`black` config for the Python side. All eleven frontend JS files rely on implicit global scope across `<script>` tags — `view`, `charts`, `INTERVENTIONS` are globals. It works, and the code is genuinely well-written, but nothing prevents a name collision as it grows. ES modules would fix this without a build step.

## E. Product opportunities (worth building, nothing broken)

These are additive — the project is already well past demo quality on the frontend.

1. **Surface the land-cover layer in the UI.** It is in the data, it is the basis of every recommendation once A2 lands, and showing "why this cell got this action" would make the tool defensible to a planner.
2. **Make the budget interactive.** Decision-Support already computes a greedy budget-capped ranking against a ₹10 crore cap (`BUDGET_RUPEES`, line 80). Expose it as a slider — "with ₹X crore, fund these cells, achieve this much cooling" is the single most compelling thing this dataset can do, and the computation already exists offline.
3. **Add a temporal dimension.** One Landsat scene is one moment. Pre-monsoon vs post-monsoon, or a summer/winter pair, would turn a snapshot into a trend and make the UHI claim far stronger.
4. **Validate the cooling model against something.** Even a crude check — do cells that WorldCover already calls tree cover run measurably cooler than adjacent built-up cells at the same elevation? — would convert `COOLING_C` from an assumption into an estimate. The data to do this is already committed.
5. **Accessibility and mobile.** The dual-map compare view is the centrepiece and is unlikely to work on a phone. Keyboard navigation of the map and a small-screen layout would widen the audience considerably.

## What is genuinely good, and should not be changed

Worth saying plainly, because most of this review is defects:

- **The frontend is excellent.** `heatField.js` implements Gaussian/Shepard interpolation with a separable running-sum box blur — O(1) per pixel regardless of radius, with bilinear splatting so the field does not snap to the accumulator lattice. That is real engineering, not a library call. The bucketed nearest-cell hit test is O(1). The temperature domain is derived from the 2nd/98th percentiles of the actual data rather than hardcoded, which is precisely the discipline that was missing everywhere else.
- **`export_grid_geojson.py`'s `validate()`** is the right instinct — fail loudly rather than ship a file the dashboard cannot render — and its `VALID_ACTIONS` check and the `keep_default_na` handling of the `"None"`/`"nan"` trap are careful work. This is the model the rest of the project should follow.
- **The commenting discipline is unusually high.** `preprocess.py`'s explanation of why the NDVI correction is mathematically non-invertible from the CSV, with a worked numeric example, is better than most production code.
- **The honesty norm.** Every module documents its own limitations without being asked. The failure here was never dishonesty — it was that five hand-maintained honest documents drifted out of sync with a codebase that kept moving. That is a process problem, and C4 is the fix.
